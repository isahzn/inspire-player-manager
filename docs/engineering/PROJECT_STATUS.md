### CR-004 Bank-transfer proofs are the bank's PDF e-receipt, verified by extraction and cross-check

- Proposed by / date: Hassen (owner), 2026-10-12 — in his words: "always ask for a PDF ... you can check the time it was transferred ... the number ... find out a way to verify that it's all been synced properly"
- Problem & requirement: before this, a proof was an opaque file nobody read, so the owner could not tell a correct transfer from a wrong amount, a reused receipt or a slip that never landed.
- Smallest proposed change: require the bank's PDF e-receipt for a bank transfer; parse it (text layer) in a sandboxed worker; cross-check its fields against the recorded payment, the invoice and the academy's own account; store findings with a parser version. Images stay supporting-only. New spec: docs/architecture/PAYMENT_VERIFICATION.md (source of truth).
- Alternatives: (a) keep proofs opaque - rejected: leaves the owner's workload and the reused-receipt/edited-amount risks in place; (b) "verify" screenshots too - rejected: no text layer, trivially edited, a pass would be fabricated; (c) send proofs to a vision/LLM API - rejected: guardian bank data leaving our infrastructure, paid third-party processing, non-deterministic answer in a money-adjacent decision; (d) auto-confirm when checks pass - rejected outright (ADR-013/ADR-020).
- Class: C2 (money-adjacent behaviour + a new parsing surface), resolved as C1-compatible API additions (PRF-04, doc_kind, findings). NOT C3: no field, status or money-rule change - payment states, allocations and receipts are untouched.
- Impact: requirements = yes (owner-requested) | DB = payment_proofs gains doc_kind/verification/checked_at; no new table | API = PRF-01 note, new PRF-04, ProofMeta/ProofFinding/ProofExtract/ProofVerification types, Payment.proofVerification rollup, SET-08 proofCheck semantics | permissions/RLS = none changed (proofs stay owner-only; extracted values are proof-class PII) | frontend = verification queue + per-proof panel + PDF-first prompt + label discipline | tests = T-VER-01..06 and a release-gate line | deploy = none | existing data = none (nothing deployed, automation has never run).
- Compatibility/migration/rollback: additive; no migration. Rollback = turn SET-08.proofCheck off (checks stop; stored findings stay historical) and stop requiring the PDF.
- Docs to update (done in this change): new PAYMENT_VERIFICATION.md -> API_CONTRACTS SS2/SS3.6 -> DATABASE SS3.1/SS3.3 -> FILES_AND_PDF SS6/SS8 -> BILLING_ENGINE SS11 -> PAGE_SPECIFICATIONS SS8 -> TESTING_AND_ACCEPTANCE (new SS2.10, T-VER-01..06, REQ-06, release gate) -> MOCK_DATA -> IMPLEMENTATION_PLAN M5/M6 -> DECISIONS (ADR-021) -> OPEN_DECISIONS (OPEN-022 resolved; OPEN-023/024/025 added) -> README -> PROJECT_STATUS.
- Decision: **Accepted** (the owner asked for it; the money boundary is unchanged) -> ADR-021. Sub-questions deliberately left to the owner rather than assumed: OPEN-023 (bank + statement export for level 3), OPEN-024 (scanned PDFs / OCR), OPEN-025 (automated "send the PDF" request).
- Implementation evidence: **plan/docs only - no code written.** Nothing to test yet; the acceptance rows are T-VER-01..06.
